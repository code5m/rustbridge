# RustBridge 主分支复查与剩余可靠性缺口闭环

日期：2026-11-05
审查基线：`5447a2c`（此前合并的 PR #22）
集中整改分支：`fix/rustbridge-completion-recovery-20261105`
合并目标：`main`（本仓库实际没有名为 `master` 的默认分支）

## 一、复查结论

2026-11-05 的 PR #22 已解决多文档状态缓存、AST 按行检索、LSP 消息队列、编译检查结果、Save All 冲突继续处理和崩溃后的编辑能力，且当时三平台 CI 通过。但是“已合并”并不等于“代码没有剩余问题”。

复查时确认：

1. `initialize_state_from_store` 同步读取至多 256 个 Journal、最多 128 MiB 的 JSON 内容；启动窗口可能被磁盘、网络文件系统、巨大 JSON 阻塞，超出硬限制的快照没有被明确告知。
2. `complete_open` 在 UI 线程上调用 `Store::load_journal`；单个 Journal 上限 64 MiB，读取和 JSON 解析足以造成操作卡顿。
3. 旧的恢复 UI 只能展示前 20 个孤立快照，导出动作在 GUI 线程上读取/写入文件。
4. 原有 `session.json` 如果损坏或过大，`load_session()` 返回 `None`；随后的周期保存可能直接替换掉仍有人工恢复价值的原始记录。
5. 新的恢复扫描和文档读取之间存在时序风险：第一个异步 Open 任务可能在保存状态 Store 绑定之前接受，此时恢复 Journal 不会被加载。
6. 文档标签切换和文件监视通知仍执行同步 `file_stamp`，遇到慢磁盘可阻塞交互。
7. Windows/macOS 原位保存的回滚副本可能在父目录同步结果未确定时被提前删除。这不意味着可以为原位写入提供真正的断电原子性。

## 二、单分支修复与设计决策

| 模块 | 本轮改变 | 数据安全边界 |
| --- | --- | --- |
| 启动恢复 | 状态目录创建、会话读取、完整 Journal 目录扫描在后台线程运行；界面有明确加载状态 | 加载完成前阻止用户操作，不会先在前台开错文件 |
| 全量索引 | 轻量 JSON 流式读取 `path` 和时间，忽略正文大字符串；完整枚举而非前 256 条；超限、损坏、不匹配及不可读计数可见 | 每个 Journal 仍限制 64 MiB；不自动删除异常文件 |
| 文档打开 | 在独立 `DocumentIo` worker 同时读取源文件和对应恢复记录；界面不复制原文来做快照比较 | 恢复仅进入独立编辑缓冲区，保存必须手动触发 |
| 第一份快照 | Store/持久化 worker 必须在第一个 Open 作业创建前就绪 | 覆盖没有 `session.json` 的崩溃恢复路径 |
| 孤立快照 | 所有条目都可通过 20 条/页浏览；导出正文时才读取，且后台操作 | 新目标使用 `create_new`，不覆盖任何已存在文件 |
| 会话兼容 | Session 严格限定大小（8 MiB）、拒绝符号链接；旧文件不可解析时，先保留为唯一命名的 `session-unreadable-*.json` 备份 | 备份失败则拒绝覆盖原状态文件 |
| 文件监视 | 后台 watcher 将检测到的文件戳传递给界面；切换标签不执行同步 `stat` | 显式保存仍验证当前真实文件内容、元数据与保存基线 |
| 保存回滚 | macOS 预先同步私有备份目录；Windows/macOS 确认目录同步结果后才尝试删除回滚副本，不确定时保留副本路径 | 不能将原位写入误称为跨平台严格断电原子替换 |
| 隐私与路径 | 状态目录必须是真实目录，不允许通过该路径的符号链接修改其他目录的权限 | 原始文件和快照不上传、不自动发布 |

## 三、增补回归测试

- 测试 300 条 Journal 同时存在时均可被索引，并报告损坏/超大文件。
- 测试错误 Journal 路径、原文件已删除但可导出、损坏会话备份。
- 测试无 Session、只有单个恢复快照时首份文档一定包含待恢复内容。
- 测试后台文档 Open 一并加载 Journal，后台文件 watcher 报告删除事件。
- 测试状态目录符号链接被拒绝且未改动原目录权限。
- 保留原有 CRLF/中文/大文件保存、SIGKILL/重启/编辑/手动保存和三平台原生测试门禁。

## 四、不能冒充“已完成”的外部或架构边界

1. 当前编辑器仍使用原有 `String`、滚动分页和单源文件 32 MiB 的安全上限，不等同于完整 Rope/Piece Table 与无限大文件编辑器。擅自重写核心存储会影响 CRLF、UTF-8、撤销、光标和持久化契约，需专门设计和基准。
2. Windows/macOS 源文件原位更新依然不能承诺掉电原子性，外部不合作写入、NFS/网络挂载卡死也没有通用严格解决方案。现有回滚与冲突检查是降低风险，不是消除物理限制。
3. Windows/macOS 实际人工桌面体验、签名证书和 Apple 公证需要真实目标环境及外部凭据；Linux Xvfb 和 CI 构建不能等同于这些验收。
4. 24 小时连续压力运行仍不能用一次 3 分钟/30 分钟检查代替；已有定期 GitHub Actions Soak 工作流可持续补足长期证据。

## 五、统一合并条件

在同一整改分支完成 `cargo fmt --check`、`cargo check --all-targets`、`cargo test --all-targets`、`cargo clippy --all-targets -- -D warnings`；Linux Release 构建及真实 GUI 编辑、崩溃恢复、资源验收；GitHub Windows、macOS、Linux 三平台原生 CI 均须通过后，才通过单 PR、单次合并进入 `main`。任何失败均回到相同分支修复，禁止跳过门禁或先部分合并。
